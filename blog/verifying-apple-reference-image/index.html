Verifying Apple Reference Images

Hidde Lycklama, Alexander Viand
Published on  02.11.2026

—

reference-image-verifier

With the new iPhone 18 Pro series, Apple created a new standard to verify the authenticity of images taken on iPhones, called Apple Reference Image. This system uses trusted hardware inside the iPhone’s camera sensor, in combination with Apple’s broader Private Compute Cloud ecosystem, in order to cryptographically certify an image as an authentic photograph. While already deployed in iOS 27 and announced on Apple’s Security Research blog 1, Apple did not provide any way to verify these images outside the iOS Photos App. Today we're presenting the first publicly available tool to inspect and verify images signed using Apple Reference Image, in addition to a deep dive into the technical details of the protocol.

AI-generated images and videos are becoming increasingly indistinguishable from genuine photographs and recordings. As a result, the visual realism of an image is no longer a reliable indicator that it depicts something that actually happened. The consequences are already visible in everyday life: manipulated images spreading misinformation on social media, AI-enhanced apartment listings in New York misleading prospective tenants about the condition of properties, and AI-edited product photos potentially concealing defects in second-hand clothing sold on platforms such as Vinted. The problem extends beyond online marketplaces. Experts from OpenAI and Meta recently warned the US judiciary that increasingly sophisticated deepfakes could make it extremely difficult to distinguish authentic audio and video evidence from fabricated material in court. With traditional methods of detecting manipulation becoming less dependable, we need a way to establish the authenticity of an image rather than merely assess whether it looks real.

One approach to this problem is to establish a cryptographic link between an image and the camera that captured it. The C2PA standard already provides a way to attach signed provenance information to images, including a record of subsequent edits. Apple, however, argues that existing implementations do not go far enough: when an image is signed only after the camera's software processing, a compromised device could already have altered its contents. Apple Reference Image therefore signs pixel data inside the camera sensor, then uses Apple's Private Cloud Compute infrastructure to turn that signed capture into a verifiable photograph. This is an interesting security design, but it is not clear that it required a separate, Apple-specific format: C2PA does not itself mandate where signing happens, and can also accommodate hardware-backed capture. For now, Apple Reference Image is unavailable in the EU, without a specific public explanation.

How to verify

Below, we will walk through the Apple Reference Image protocol and how to verify it, using an interactive example. If you have an image from an iPhone 18 Pro series phone, you can upload it (technically, everything is processed locally in the browser) and use it for this explainer, otherwise we provide an example image.

One key difference between C2PA and the Apple Reference Image solution is that the latter does not actually certify the image that the user generally sees when the image is rendered. Instead, it embeds a second, separate reference image into the image file container as special metadata. Any cryptographic guarantees are only made about this reference image, which is only accessible with special viewers (e.g., the iOS 27 and newer Photos App, or our verification tool). Notably, even in a fresh iPhone photo, the user-facing image and the reference image are not exactly the same, with the latter lacking some of the contrast/saturation/etc adjustments that are applied to the user-facing image.

The rest of this post walks through what the verifier checks and how in more detail.

What Apple says

Apple's description of the system [Apple26] has two phases. In the first, the camera sensor is booted into a reference capture mode and signs the captured frame together with its metadata, using a key that was generated inside the sensor at the factory. The Secure Enclave adds a second signature over OS-level metadata such as exposure and lens parameters, and timestamp tokens bound the capture time from both sides. The result is a signed digital negative in DNG format.

In the second phase, the negative is uploaded to Private Cloud Compute (PCC), Apple's attested server environment. PCC verifies the chain of signatures, develops the negative into a JPEG, computes a confidence score, and hashes the JPEG. It then submits that hash to an Apple signing service, which signs it with "a composite post-quantum signature combining RSA-3072 and ML-DSA-87". The signature is embedded in the JPEG. The same hash also supplies the bits for a photo GUID that Apple can put on a revocation list, so that images from misbehaving sensors can be invalidated after the fact.

That is where the public description ends. Which bytes are hashed, with which function, in which order, and how the signature and certificates are laid out in the file, is not documented. Neither is the root certificate that a verifier would need to trust.

Where the reference image is stored

A photo taken in Reference Image mode can leave the phone as a HEIC file or as a JPEG export. In both cases the outer image is an ordinary photo. A flag in Apple's MakerNote (tag 0x0063 with value 8) marks it as a developed Reference Image.

The signed object is a separate baseline JPEG of 3024 by 4032 pixels. In a HEIC file it is stored as its own item of type uri, identified as tag:apple.com,2025:photo:metadata:provenance:processedimage, and linked to the primary image with a cdsc reference. In a JPEG export it is split across 39 APP3 segments with a 4-byte sequence header each. Concatenating the segments and dropping a leading 4-byte field yields the reference image, about 2.5 MB for the example photo.

The figure below shows the nesting for the current photo, from the outer container down to the signature.

Inside the reference image, three APP11 segments carry JUMBF boxes. JUMBF is the same container format that C2PA uses, which is probably why early reports assumed the two were related. The box UUIDs are Apple-private, there is no C2PA manifest, and C2PA tools do not verify these files [C2PAViewer26]. Box 1 is a header that indexes the other boxes and records the format version (1.3 in our samples). Box 2 holds three Unix timestamps. Box 3 is the signature box: a 5 KB composite signature, a 17 KB bundle with two certificates, and a short trailer with the development time.

Which bytes are signed

Apple's announcement says that PCC hashes the JPEG and signs the hash. The obvious reading is that the signature covers the file with the signature itself cut out or zeroed, as in PDF or Authenticode, or with a range exclusion as in C2PA. None of these is what Apple does, and it cost us a brute-force search of about 1.4 million hash layouts per photo to be sure of it (more on that below).

The actual recipe splits the reference image into three ranges at the signature box and hashes each with SHA-512:

P = SHA-512( jpeg[0 : box3.start] )                         # preamble
S = SHA-512( jpeg[box3.start : box3.end] minus excluded )   # signature box
C = SHA-512( jpeg[box3.end : EOF] )                         # pixel data
CombinedHash = SHA-512( P || S || C )

Here box3 is the whole APP11 segment that carries the signature box, marker and length included, and excluded is just the u32 length field and the DER-encoded signature that follows it. Excluded bytes are skipped, not zeroed: the bytes before and after are concatenated and hashed as one stream. Everything else in the signature box, including both certificates and the development timestamp, is covered by the signature. Swapping in a different certificate therefore breaks verification.

The byte map shows which bytes of the current photo's reference image feed which hash. Hover a segment to find it in the table.

Inside the signature box and the timestamps

The preamble also contains the JFIF and Exif headers, an ICC profile and an Apple AROT segment of unknown purpose. All of it is signed, but note what is not: the outer photo's pixels and metadata are not part of any of the three ranges.

The signature

The 64-byte CombinedHash is the only thing the signing service ever sees. It is signed with id-MLDSA87-RSA3072-PSS-SHA512, the composite scheme standardised by the IETF LAMPS working group [LAMPS]. A composite signature is two signatures over the same message by two independent algorithms, and it is only valid if both verify. The idea is a belt-and-braces transition to post-quantum cryptography: if ML-DSA turns out to have a flaw, RSA still stands, and if a large quantum computer breaks RSA, ML-DSA still stands.

The message that both halves sign is not the hash itself but a small wrapper, M', which prefixes it with a fixed domain-separation string, the algorithm label, and an application context. Apple leaves the context empty.

M' = "CompositeAlgorithmSignatures2025"            # 32 bytes
   || "COMPSIG-MLDSA87-RSA3072-PSS-SHA512"         # 34 bytes
   || 0x00                                         # context length 0
   || CombinedHash                                 # 64 bytes

The ML-DSA-87 half [FIPS204] is a pure-mode signature over M' with the label as context string, 4627 bytes long. The RSA half is a 3072-bit RSASSA-PSS signature over M' with SHA-256, MGF1-SHA-256 and a 32-byte salt, 384 bytes long. The figure below traces the current photo from the three range hashes to the two verified halves.

The last row is the composite rule at work: the RSA half still verifies because the excluded bytes are not hashed, but the broken ML-DSA half is enough to reject the photo.

Who signed it

The signature box carries two certificates: the signer, and the issuing CA that signed it. Both are themselves signed with the same composite construction. The chain ends at Apple Prove ML-DSA RSA Root CA G1, a root that Apple created on 18 March 2026 and does not publish. It is not on Apple's certificate authority page, and its URL on certs.apple.com returns a 404. We found it as a trust anchor in the certificate bundle of iOS 27.1, and our verifier pins its public key and fingerprint rather than distributing the certificate itself.

Two details matter for what a valid signature means. First, both of our sample photos carry the same signer certificate. The signer is Apple's development service, not the capturing iPhone. A valid Reference Image signature therefore says "Apple's pipeline developed this from a negative it accepted", not "this particular device took this photo". Second, the SecTrust policy iOS evaluates for this chain goes by the internal name ProvoloneProcessedSigning, and iOS additionally rejects provenance for photos developed more than five years ago and checks a per-photo digest against a revocation list. Our verifier reproduces the signature and chain checks but not the revocation query, the policy constraints or the age limit, and it says so in its report.

How we found the recipe

The certificate chain verified immediately with the textbook composite construction, so for the image signature only the message seemed open. We tried every plausible candidate: the reference image with the signature removed or zeroed, with only the signature box removed, the scan data alone, the decoded pixels in sixteen hundred decoder and layout combinations, and a brute-force sweep of about 1.4 million combinations of segment subsets, inner digests and guessed context strings per photo. The sweep was feasible because RSA-PSS verification exposes the salt: one public-key operation recovers the hash and salt from the signature, after which each candidate message costs two SHA-256 calls instead of a full ML-DSA verification. Nothing matched.

The problem was that we were guessing at a single hash, and the answer is a hash of three hashes. No linear hash over any byte subset reproduces it.

So we went looking for Apple's own verifier. macOS 26 has no verifier for these files. The iOS simulator contains the full Photos code path, parses the file, and then logs verification skipped, API unavailable (simulator=1): the provenance code in CMPhoto.framework is stubbed out in the simulator. What the simulator did give us was the root certificate, in its trust store.

In the end we downloaded the iOS 27.0.1 firmware for the iPhone 18 Pro, extracted its 8 GB dyld shared cache, and disassembled CMPhoto. The function names gave the game away: PreambleHash, SignatureParametersHash, ContentHash, CombinedHash. One last trap remained. We first misread the order in which the three digests are concatenated and lost hours to P || C || S. With the order read correctly as P || S || C, both photos verified on the first try, with both halves of the composite signature and the full chain up to the root.

What this means

The signature covers a hidden image, not the one you see. The reference image is a faithful but plain rendition of the negative; the outer photo is what the camera app shows and shares. A valid signature proves that the file carries an image that Apple's pipeline signed. It does not prove that the visible pixels match it. A viewer can compare the two by eye, as you can above, but that comparison is not cryptographic. Any tool that reports a Reference Image as "intact" after checking only the outer pixels is measuring the wrong thing.

The signer is a service. One key signs many photos, so the signature attests to Apple's development pipeline, not to a device. That is a deliberate privacy choice, and Apple's design puts device attestation in the negative rather than in the shared image, but it changes what a reader should expect from "signed by the camera".

It is post-quantum, and it is not C2PA. This is a real deployment of the final IETF composite construction with an empty context, and the tamper test above is a neat demonstration of why both halves have to pass. The carrier looks like C2PA, but the boxes, the hashing and the trust model are Apple's own.

Verification depends on Apple. The root certificate exists only inside iOS, revocation is an online check against an Apple service, and the format is undocumented. For a system whose purpose is trust, independent verification should not require firmware disassembly. We hope Apple publishes the specification and the root, and until then our verifier is available for anyone to use and audit.

Open questions

A few things we saw in the code but have not confirmed on real files:

  • How the per-photo digest for the revocation check is derived, and what the check reveals to Apple.
  • What the three timestamps in box 2 mean. The first precedes the capture by several minutes, plausibly a pre-fetched timestamp token; the last equals the development time in the trailer.
  • The purpose of the AROT segment and why the reference image declares a CFA photometric interpretation.
  • A second verification path in CMPhoto with a Basic Attestation root, probably for device-signed negatives, which we did not investigate.

Everything above was tested on two photos from one iPhone 18 Pro with format version 1.3, against the CMPhoto of iOS 27.0.1 and the root from iOS 27.1.

Use the verifier

The standalone verifier lives at pps-lab.com/apple-reference-image-verifier. Its verification logic is the reference-image npm package, which runs in Node and the browser, makes no network requests, and produces a JSON report of everything shown in this post:

npx reference-image IMG_0071.JPG
npx reference-image --json IMG_0073.HEIC > report.json
